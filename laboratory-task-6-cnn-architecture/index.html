Laboratory Activity 6¶

Instruction: Convert the following CNN architecture diagram into a PyTorch CNN Architecture.

The diagram describes a four-convolution CNN, heavier than the two-convolution example built earlier in this notebook: Conv1 → MaxPool1, then Conv2, Conv3, Conv4 → MaxPool2, a Dropout, and three fully connected layers ending in SoftMax. Before writing the nn.Module, the sections below work out the "?" spots in the diagram using the same calc_out() helper defined earlier in this notebook, then build and train the model on MNIST so the architecture is checked against real data rather than just typed in and hoped for.

3. Working Out the Diagram's "?" Shapes¶

Reusing calc_out() from earlier in this notebook, each layer's spatial output size can be worked out directly from its kernel, stride and padding, the same way the two-convolution demonstration model's shapes were checked.

def calc_out(w, f, s, p):
    """Output size of a square input after a square-kernel convolution or pooling op."""
    out = (w - f + 2 * p) // s + 1
    print(f'Output Shape: {out}')
    return out

Conv1 (kernel 3, stride 1, padding 1) on the 28×28 input:

calc_out(28, 3, 1, 1)  # Conv1
Output Shape: 28
28

A 3×3 kernel with padding 1 and stride 1 always preserves the input size, so Conv1's output is 32×28×28 — 32 channels (as labeled on the block), still 28 rows and columns. This matches the one shape the diagram actually fills in for that block.

MaxPool1 (kernel 2, stride 2, padding 1) on that 28×28 map:

calc_out(28, 2, 2, 1)  # MaxPool1
Output Shape: 15
15

That comes out to 15×15, not 28×28. The diagram's first shape label, (32, 32, 28, 28), appears to only describe the state right after Conv1, before MaxPool1 is applied — a stride-2 pool cannot leave the spatial size unchanged. The 15×15 figure from calc_out() is the one actually used below, and it is what feeds into Conv2.

Conv2, Conv3, Conv4 all use kernel 3, stride 1, padding 1, so, like Conv1, each one preserves whatever spatial size it receives:

calc_out(15, 3, 1, 1)  # Conv2, Conv3, and Conv4 all preserve the spatial size
Output Shape: 15
15

So the feature map stays 15×15 through Conv2, Conv3 and Conv4, only the channel count changes at each step (32→64→128→256, per the diagram's labels). MaxPool2 (kernel 2, stride 2, no padding) is what finally reduces the spatial size again:

calc_out(15, 2, 2, 0)  # MaxPool2
Output Shape: 7
7

That gives a final feature map of 256×7×7 heading into Dropout and then the flatten step, for 256 × 7 × 7 = 12,544 features going into FCN1. That resolves every "?" in the diagram:

flat_features = 256 * 7 * 7
print("Flattened feature count (FCN1 input):", flat_features)
Flattened feature count (FCN1 input): 12544

  • Conv2 output: (64, 15, 15)

  • Conv3 output: (128, 15, 15)

4. Building the Architecture¶

Following the diagram block by block: two convolutions plus a max-pool, two more convolutions, another max-pool, dropout, flatten, then three fully connected layers with the activation the diagram places on each one — ReLU on the first two, softmax on the last.

One thing worth flagging: nn.CrossEntropyLoss, used further down as the criterion, expects raw, un-normalized scores (logits) and applies its own log_softmax internally. Since the diagram explicitly puts a SoftMax at the end of FCN3, applying softmax twice is technically redundant — though it is also exactly what the two-convolution demonstration model earlier in this notebook does, so the same convention is kept here for consistency with the rest of the notebook rather than silently deviating from the diagram.

class DiagramCNN(nn.Module):
    def __init__(self, n_classes=10):
        super().__init__()

        # Block 1: Conv1 -> ReLU -> MaxPool1
        self.conv1 = nn.Conv2d(in_channels=1, out_channels=32, kernel_size=(3, 3), stride=1, padding=1)
        self.pool1 = nn.MaxPool2d(kernel_size=(2, 2), stride=2, padding=1)

        # Block 2: Conv2 -> ReLU, Conv3 -> ReLU, Conv4 -> ReLU -> MaxPool2
        self.conv2 = nn.Conv2d(32, 64, kernel_size=(3, 3), stride=1, padding=1)
        self.conv3 = nn.Conv2d(64, 128, kernel_size=(3, 3), stride=1, padding=1)
        self.conv4 = nn.Conv2d(128, 256, kernel_size=(3, 3), stride=1, padding=1)
        self.pool2 = nn.MaxPool2d(kernel_size=(2, 2), stride=2, padding=0)

        # Regularization + classifier head
        self.dropout = nn.Dropout(p=0.2)
        self.fcn1 = nn.Linear(256 * 7 * 7, 1000)
        self.fcn2 = nn.Linear(1000, 500)
        self.fcn3 = nn.Linear(500, n_classes)

    def forward(self, x):
        x = F.relu(self.conv1(x))
        x = self.pool1(x)

        x = F.relu(self.conv2(x))
        x = F.relu(self.conv3(x))
        x = F.relu(self.conv4(x))
        x = self.pool2(x)

        x = self.dropout(x)
        x = x.view(x.size(0), -1)  # flatten

        x = F.relu(self.fcn1(x))
        x = F.relu(self.fcn2(x))
        x = F.softmax(self.fcn3(x), dim=1)

        return x

def count_parameters(model):
    params = [p.numel() for p in model.parameters() if p.requires_grad]
    for item in params:
        print(f'{item:>9}')
    print(f'__________\n{sum(params):>9}')

As expected, almost all of it — over 12.5 million of the 13.4 million parameters — sits in FCN1 alone, since it connects every one of the 12,544 flattened features to 1,000 hidden units. The four convolutional layers combined only account for about 388,000 parameters, despite doing most of the actual feature extraction. This is a common shape for CNNs built this way: convolutions are parameter-efficient because their weights are shared across spatial positions, while a dense layer bridging a large flattened map to a wide hidden layer is not.

A forward pass on a real batch confirms the architecture actually runs end to end and that the output shape and scale line up with what is expected: one row per image, 10 columns (one score per digit), and — because of the softmax — each row summing to 1.

7. Training¶

This model is trained for a single epoch. That is a deliberate limitation of the CPU this environment runs on, not a claim that one epoch is generally sufficient — with roughly 13.4 million parameters and no GPU available, more epochs would take considerably longer to run here. MNIST is forgiving enough that even one pass over 48,000 images is enough to show the loss dropping and the accuracy climbing well above chance, which is what this step is meant to confirm: that the architecture, as translated from the diagram, actually learns.

def evaluate(model, loader):
    model.eval()
    correct = 0
    total = 0
    running_loss = 0.0
    with torch.no_grad():
        for xb, yb in loader:
            xb, yb = xb.to(device), yb.to(device)
            out = model(xb)
            loss = criterion(out, yb)
            running_loss += loss.item() * xb.size(0)
            preds = out.argmax(dim=1)
            correct += (preds == yb).sum().item()
            total += xb.size(0)
    return running_loss / total, correct / total
set_seed(42)
epochs = 1

train_losses, train_accs = [], []
val_losses, val_accs = [], []

start_time = time.time()

for e in range(epochs):
    model.train()
    running_loss = 0.0
    correct = 0
    total = 0

    for b, (xb, yb) in enumerate(train_loader):
        xb, yb = xb.to(device), yb.to(device)

        optimizer.zero_grad()
        out = model(xb)
        loss = criterion(out, yb)
        loss.backward()
        optimizer.step()

        running_loss += loss.item() * xb.size(0)
        preds = out.argmax(dim=1)
        correct += (preds == yb).sum().item()
        total += xb.size(0)

        if (b + 1) % 100 == 0:
            print(f"epoch {e + 1} | batch {b + 1:4}/{len(train_loader)} | "
                  f"running loss: {running_loss / total:.4f} | running acc: {correct / total:.4f}")

    train_loss = running_loss / total
    train_acc = correct / total
    val_loss, val_acc = evaluate(model, val_loader)

    train_losses.append(train_loss)
    train_accs.append(train_acc)
    val_losses.append(val_loss)
    val_accs.append(val_acc)

    print(f"\nEpoch {e + 1}/{epochs} | train loss: {train_loss:.4f}, train acc: {train_acc:.4f} "
          f"| val loss: {val_loss:.4f}, val acc: {val_acc:.4f}")

9. Recap¶

The diagram's blocks map onto DiagramCNN one to one: conv1/pool1, conv2/conv3/conv4/pool2, dropout, the flatten step, and fcn1/fcn2/fcn3, with ReLU or softmax applied exactly where the diagram places it. The "?" spatial dimensions resolved to 15×15 after the first pool and 7×7 after the second, which is what fixed FCN1's input size at 12,544. With about 13.4 million parameters, a single epoch on a CPU-only machine was enough to move well past chance accuracy on the test set, which is the main thing this exercise was checking — that the diagram, translated literally into PyTorch layers, is a working network and not just a picture.
